# Chenile Process Management

Chenile Process Management is a splitter/aggregator (map-reduce) orchestrator built on Chenile's
state-machine (STM / Finito) framework. A long-running job is a tree of `Process` entities: a non-leaf
process splits into sub-processes, each sub-process may split further, leaf processes execute real work,
and results aggregate back up until the root is complete. The flow is declared once in a state-transition
XML file; work is performed by pluggable workers that run outside the STM and report back by raising events.
It runs as a library inside a Spring application backed by the application's own database, and also ships a
runnable administration server and a React admin console.

Long-form guides in the repo: `docs/process-management.md`, `docs/process-management-diagrams.md` (sequence +
ER diagrams), `docs/process-management-ui.md` (management API + UI + admin server),
`docs/temporal-comparison.md`, `docs/process-outbox.md` (operations), and
`docs/adr/0001-durable-outbox-for-process-entry-action.md`. Deployment topology:
`docs/deployment.md`, `docs/deployment-presentation.md` (slide/video outline),
`docs/deployment-schematic.html` (animated), `docs/blueprints/process-deployment-blueprint.md` (how the
jgen blueprints realize this topology). The deployment is generated by the **`chenile-process-management`**
jgen blueprint (2.1.35, in `chenile-gen/jgen/bp-process-management`), which composes `minimonolith` +
**`chenile-process-worker-set`** to emit server + one shared worker-listener + per-definition worker JARs over Kafka — see
the `chenile-jgen` skill. State diagram: `docs/puml/process-states.mermaid`, matching
`process-service/src/main/resources/org/chenile/orchestrator/process/process-states.xml`.

## Modules (Maven reactor)

- **process-api** — model (`Process`, `ProcessDto`, `WorkerDto`, `WorkerType`, `Constants`, payloads,
  `ProcessCompletedEvent`), `WorkerStarter`, config abstraction (`IProcessConfigurator`, `ProcessDef`,
  `ProcessConfigurator`), `ProcessDefinitionService`, and (2.1.35) the queue work contract in
  `org.chenile.orchestrator.process.workers`: `WorkListenerService<T>.accept(processType, workerType,
  WorkListenerInput<T>)`, `WorkListenerInput<T> {processId, dispatchId, payload, execDef}`,
  `WorkerConstants.PROCESS_TYPE/WORKER_TYPE` header names.
- **process-service** — running service: STM, the process-side outbox commands + producer,
  `ProcessManagerImpl`, controllers, `ProcessEntryAction`, configurators, the management API.
- **chenile-outbox** — the general-purpose durable transactional outbox infrastructure (was
  `process-outbox`; Maven module/artifact renamed, Java package unchanged
  `org.chenile.orchestrator.process.outbox`). Holds `OutboxCommand`, `OutboxCommandLifecycle`,
  `OutboxCommandProducer`, `OutboxCommandRegistry`, `OutboxDispatcher`, `ProcessOutboxRepository`,
  `OutboxRetryPolicy`. It is NOT process-specific — triggers use the same outbox.
- **process-delegate** — remote client for the manager (`ProcessManagerClient` + `DelegateConfiguration`)
  AND the worker base classes. **Current (2.1.35):** the typed listeners in `org.chenile.orchestrator.process.worker`
  — `ExecutorWorkListener<In,Out>`, `SplitterWorkListener<In,ChildIn>`, `AggregatorWorkListener<In,Out,ChildOut>`
  on `AbstractWorkListener` — plus `ProcessWorkServiceSelector`, `ProcessWorkBodyTypeSelector` and
  `ProcessWorkServiceFallback`. **Legacy:** `SplitterBase`/`ExecutorBase`/`AggregatorBase`/`BatchServiceBase` under
  `org.chenile.orchestrator.process.utils.base` (WorkerDto-based; no longer wired by `DelegateConfiguration`).
  There is no separate process-utils module.
- **invm-process-starter / q-based-process-starter / jdbc-process-starter** — three interchangeable worker
  launch strategies (`WorkerStarter` impls).
- **trigger-api** — trigger contracts/DTOs (`TriggerService`, `TriggerInput`, `TriggerResult`,
  `TriggerStatus`). `TriggerService` = `trigger(TriggerInput)` + `status(String triggerId)`. (No
  `TriggerObserver` — removed.) `TriggerResult` implements `ResponseHeadersAware` (header-aware response).
- **trigger-service** — `EventTriggerService` + `DispatchTriggerCommand` + `TriggerController`. Triggers are
  durable `DISPATCH_TRIGGER` outbox commands; there is NO `trigger_log` table and no separate trigger store.
- **crontab-api / crontab-service** (formerly one `crontab-trigger` module) — durable Quartz crontabs on
  `chenile-scheduler`; `CrontabReader` with DB (`CrontabRepository`) and JSON (`JsonCrontabRepository`) backends,
  plus `CrontabValidator`. `CrontabScheduler` fires `TriggerService.trigger(...)`.
- **process-admin-server** — runnable Spring Boot host bundling controllers, trigger + crontab modules, the
  **in-VM** starter, the management API, and the scheduler. By design it ships no business workers (a
  `START_WORKER` no-ops, so a leaf sits in EXECUTING); it runs the engine/API/scheduler, and production
  deployments are generated with the `chenile-process-management` jgen blueprint (server + Kafka worker-listener
  + worker JARs). It depends on `invm-process-starter`, not `jdbc-process-starter`.
- **process-ui** — React + Vite administrator console consuming the management API. The crontab form has a
  Quartz cron-expression builder (interval / hourly / daily / weekdays / weekly / monthly → e.g.
  `0 0/5 * * * ?`, `0 30 9 ? * MON-FRI`); the generated expression stays editable.

`trigger-service` and the crontab modules are optional in `process-service`; applications select them
explicitly. There is no `chenile-logger` module.

## Domain model

`Process`: `leaf`, `processType`, `parentId`, `predecessorId`, `triggerId`, transient `subProcesses`,
`splitCompleted`, counters `numSubProcesses` / `numCompletedSubProcesses`, `input` / `output`, an `errors`
collection, and the inherited `tenant`. The current STM state (and `stateEntryTime`) live on the entity. No
`dormant`/parked state or `activate` event.

## State machine (PROCESS_FLOW)

```
[*] --> isThisLeafNode
isThisLeafNode --> EXECUTING        : leaf == true
isThisLeafNode --> SPLIT_PENDING    : leaf == false

EXECUTING --> EXECUTING             : statusUpdate            (self, progress)
EXECUTING --> PROCESSED             : doneSuccessfully
EXECUTING --> PROCESSED_WITH_ERRORS : doneWithErrors

SPLIT_PENDING --> SUB_PROCESSES_PENDING : splitPartiallyDone / splitDone
SPLIT_PENDING --> PROCESSED_WITH_ERRORS : splitDoneWithErrors

SUB_PROCESSES_PENDING --> SUB_PROCESSES_PENDING : splitPartiallyDone
SUB_PROCESSES_PENDING --> areAllSubProcessesDone : splitDone / subProcessDoneSuccessfully / subProcessDoneWithErrors
areAllSubProcessesDone --> AGGREGATION_PENDING   : numSubProcesses == numCompletedSubProcesses && splitCompleted
areAllSubProcessesDone --> SUB_PROCESSES_PENDING : otherwise

AGGREGATION_PENDING --> areThereErrors             : aggregationDone
AGGREGATION_PENDING --> PROCESSED_WITH_ERRORS      : aggregationDoneWithErrors
areThereErrors --> PROCESSED_WITH_ERRORS : errors.size() > 0
areThereErrors --> PROCESSED             : errors.size() == 0

PROCESSED, PROCESSED_WITH_ERRORS are terminal.
```

Guard `(numSubProcesses == numCompletedSubProcesses) && splitCompleted` advances a parent to aggregation
only when the split is finalized **and** every child reported back.

## Lifecycle

```
Trigger (crontab or any adapter)
  -> TriggerService.trigger(TriggerInput)   [enqueues a durable DISPATCH_TRIGGER outbox command; commits
                                             acceptance in a REQUIRES_NEW tx, returns the outbox row id]
  -> outbox dispatcher later runs DispatchTriggerCommand.dispatch
  -> EventProcessor.handleEvent("ProcessCreate", ProcessDto, headers)   [x-chenile-trigger-id = command id]
  -> ProcessManagerImpl.create(ProcessDto)   [creates a root; retains trigger correlation]
  -> root Process persisted, STM entered
  -> matching SPLITTER / EXECUTOR / AGGREGATOR worker launched (via START_WORKER command + WorkerStarter)
  -> workers raise events back into the STM
  -> children created, parents notified, state advances
  -> terminal state (PROCESSED / PROCESSED_WITH_ERRORS)
  -> ProcessCompleted emitted (EMIT_COMPLETED) -> successors chained as new processes
```

See `docs/process-management-diagrams.md` for a full sequence diagram and an ER diagram of the data model.

## Creating a process

`ProcessController.create` is `@EventsSubscribedTo("ProcessCreate")`, reachable via `POST /process` or the
in-JVM `ProcessCreate` event, body `ProcessDto` (`processDefName`, `args`, `triggerId`, `description`).
`ProcessManagerImpl.create(ProcessDto)` requires `processDefName`, serializes `args` into `input`, records
`triggerId` (payload or `x-chenile-trigger-id` header), and drives the root through the STM. `triggerId` is
correlation only; dedup of repeated activations is the trigger/outbox layer's job. Endpoints: `GET /process/{id}`,
`PATCH /process/{id}/{eventID}`, `GET /processChildren/{id}`, `POST /process/completed`.

## Workers and launch modes

`StartWorkerCommand` resolves the worker for the current state and hands a `WorkerDto` to the configured
`WorkerStarter` (same `ProcessDef.config` map, copied, for every worker type): `SPLIT_PENDING`→`SPLITTER`,
`EXECUTING`→`EXECUTOR`, `AGGREGATION_PENDING`→`AGGREGATOR`. Three `WorkerStarter` impls: **in-VM**
(`EventProcessor.handleEvent`), **queue-based** (`QueueBasedProcessStarter` → `ChenilePub.asyncPublish` to a
topic from `execDef.get("queue")`), **JDBC** (durable `chenile_process_work_item`: idempotency key,
`FOR UPDATE SKIP LOCKED`, lease, attempt/retry, `DEAD`; a runner polls — production-grade, KEDA-scalable).

Queue message (2.1.35): `start()` publishes a **`WorkListenerInput` JSON envelope** `{processId, dispatchId,
payload, execDef}` (payload = the process input as a JSON tree) with headers: every `x-` context header, the
tenant `x-chenile-tenant-id` set explicitly from `process.tenant`, and **`processType`** + **`workerType`**.
`headers(WorkerDto)` is a protected extension point. The old `WorkerDto` body survives as `start1()` (legacy).

Workers (typed listeners) autowire `ProcessManagerClient` and report back via
`splitDone`/`splitPartiallyDone`/`doneSuccessfully`/`aggregationDone`; their own failures become the matching
`...WithErrors` event (see the 2.1.35 section).

## Process definitions

`ProcessDef`: `leaf`, `parentProcessType`, chaining (`predecessorProcessType`, `predecessorArgs` =
`INPUT`/`OUTPUT`/`BOTH`), and one `config` map for all worker types (includes `queue` for the q-based starter).
Resolved via `IProcessConfigurator.findByName`; source chosen by `chenile.process.configurator` = `json`
(default, `def.json`) or `database` (`process_definition` table). `ProcessConfigurator.read(stream,
documentType)` supports a typed subclass of `Processes` with a `validate(...)` hook for extended definition
documents. (jgen's process blueprint feeds this a native `processMap` spec plus a separate `cronSpec`.)
`ProcessDefinitionService` (process-api; create/update/retrieve/findAll) is the edit path: it validates
predecessor-chain and parent-hierarchy cycles and invalidates the configurator cache after commit; JSON-backed
deployments are read-only. Definitions are **global** (keyed by process type, not tenant).

## Durable execution, the general-purpose outbox, and the command registry

**The durable transactional outbox is always on — there is no enable flag and no inline mode.** Every process
transition saves its state and records its consequences atomically: `ProcessEntryAction` never executes
effects inline; each consequence is a row in `chenile_process_outbox` written **in the same transaction that
saves the Process**, and a scheduled poller drains and dispatches them. The same outbox also carries triggers.

**Two concepts, cleanly separated** (generalized in the chenile-outbox rework):

- **Producers** decide WHAT to enqueue, per context type. `OutboxCommandProducer<C>` holds the lifecycles for
  one context type and, for a given context, calls each command's `shouldEnqueue(context)` (eligibility, no
  writes) then `enqueue(context)`. Two producers:
  - `OutboxCommandProducer<ProcessTransition>` (bean `processOutboxCommands`) over the four process commands,
    ordered `@Order(0..3)`: `CreateSubProcessCommand`, `SignalParentCommand`, `EmitCompletedCommand`,
    `StartWorkerCommand`. `ProcessEntryAction` calls `commands.enqueue(new ProcessTransition(process, toState))`.
  - `OutboxCommandProducer<OutboxCommand>` built inside `EventTriggerService` over the single
    `DispatchTriggerCommand`, which implements `OutboxCommandLifecycle<OutboxCommand>` directly — the trigger
    builds an `OutboxCommand` itself, so there is no wrapper/`Submission` type; `shouldEnqueue` matches on
    `commandType == DISPATCH_TRIGGER`.
- **The registry + dispatcher** decide HOW to run a persisted row, independent of context type. One
  `OutboxCommandRegistry` maps every `OutboxCommandLifecycle<?>.type()` string → lifecycle (duplicate type
  fails at startup; unregistered persisted type → error → retry → DEAD). One `OutboxDispatcher` drains the one
  `chenile_process_outbox` table and resolves each row's `command_type` with `registry.resolve(type)`.

`OutboxCommandLifecycle<C>`: `type()`, `shouldEnqueue(C)` (default true, no writes), `enqueue(C)`,
`executionHeaders(OutboxCommand)` (default empty; persisted invocation headers the execution boundary installs),
`dispatch(OutboxCommand)`, `onDead(OutboxCommand)` (best-effort, after DEAD commits, own transaction).
**Five command types total**: `CREATE_SUBPROCESS`, `SIGNAL_PARENT`, `EMIT_COMPLETED`, `START_WORKER` (process
side), and `DISPATCH_TRIGGER` (trigger side). The execution boundary is `ProcessOutboxRepository.handleAndComplete`:
it installs `executionHeaders` + tenant, snapshots/restores context, and retains it through commit. So
`AbstractProcessOutboxCommand.dispatch`/`onDead` only need their own tenant install for the direct-call path
(`ProcessCommandTenantTest`); `DispatchTriggerCommand` supplies headers via `executionHeaders` and keeps
`dispatch` to just the `handleEvent` call — no manual `TransactionSynchronization`.

Retry with exponential backoff to a max attempt count, then `DEAD` (`deadCount()`, `replayDead(id)`), invoking
the command's `onDead` (default: operator replay; `StartWorkerCommand` overrides it to drive the process to
the error terminal). Reference DB **PostgreSQL** (`ON CONFLICT DO NOTHING`); H2 PostgreSQL-mode for tests.
`ProcessManagerImpl` wraps create/processById/processCompleted in REQUIRED transactions and `lockById` locks
the process before applying events.

The repository (`ProcessOutboxRepository`) is **hand-written JDBC / native SQL by design, not JPA** — see the
gotchas and `docs/process-outbox.md` ("Why the repository is JDBC, not JPA").

### Idempotency guards (three distinct, don't conflate)

Durable delivery is at-least-once; correctness rests on three separate guards:

1. **Enqueue de-duplication — outbox `idempotency_key` (unique).** Stops the same consequence being enqueued
   twice. **This is also the trigger idempotency guard** now that triggers are outbox commands: a trigger's
   key is `trigger:<id>` (unique, not deduped) when the caller gives no `idempotencyKey`, or
   `trigger:<sha256(tenant, eventId, idempotencyKey)>` when they do; **cron** sets
   `idempotencyKey = "crontab:<crontabId>:<quartzFireInstanceId>"`, so each fire instance is deduped here.
2. **Claim-token fencing — `claim_token` + lease (`FOR UPDATE SKIP LOCKED`).** Exactly one winning claimant
   per attempt; a reclaimed row's loser cannot ack/fail/keep its effect.
3. **Effect-level idempotency — `checkIdempotency(consumer, key)` against `chenile_process_receipt`.** THE
   idempotency check (method on `ProcessOutboxRepository`, helper on the abstract process command). Atomic
   `insert ... on conflict do nothing` → `true` first time (run effect), `false` if the key existed (skip),
   committed in the SAME transaction as the effect + DONE ack. Keyed by business identity:
   - `PARENT` → `[parentId, childId]`: `numCompletedSubProcesses` counts each child once even across
     success-then-error or replay; load-bearing.
   - `CHAIN` → `[predecessorId, successorType]`: prevents duplicate successors on a replayed `EMIT_COMPLETED`.
   - `CREATE` → `create:{childId}` (also deterministic id + `existsById`).
   - `WORKER` → `{processId}:{workerType}` (receivers can also dedupe on `dispatchId`, carried in `WorkListenerInput`).

`chenile_process_receipt` is retained for these guarantees; append-only, prune on a retention horizon no
shorter than the maximum time a `DEAD` command could be replayed. Non-transactional effects (broker publish,
after-commit fan-out) stay at-least-once; dedupe at the receiver.

## Triggering (unified onto the outbox — no trigger_log)

A **trigger is a durable event invocation**, independent of processes and cron, carried as a
`DISPATCH_TRIGGER` outbox command. There is NO `trigger_log` table, no `TriggerLog`/store layer, and no
`TriggerObserver` (all removed).

`EventTriggerService.trigger(TriggerInput)`:
- Collects `x-*` headers from context + input, resolves/validates tenant (`x-chenile-tenant-id`), strips any
  incoming `x-chenile-trigger-id` (callers cannot spoof the accepted identity).
- Builds a `Trigger` envelope `{ eventId, triggerTime, headers, triggerContext, payload }`, assigns a
  server-generated UUID `id`, computes the idempotency key (see guard #1).
- Enqueues the `OutboxCommand` (type `DISPATCH_TRIGGER`, `processId = null`, `tenantId`, payload = envelope JSON)
  in a **REQUIRES_NEW acceptance transaction** — durable acceptance commits before returning — and returns the
  accepted outbox row id as `TriggerResult.triggerId`.

`DispatchTriggerCommand` implements `OutboxCommandLifecycle<OutboxCommand>`; `executionHeaders` returns the
trigger headers + `x-chenile-trigger-id` + tenant (the repository boundary installs them), and `dispatch`
just calls `EventProcessor.handleEvent(eventId, payload, headers)`; no subscriber or a subscriber exception →
retry → `DEAD` (same semantics as process commands).

`status(triggerId)` reads the `DISPATCH_TRIGGER` row by id (tenant-filtered) and returns a `TriggerStatus`
(status, attempt, trigger/created/started/finished times, error, source from `x-chenile-trigger-source`,
triggerContext, payload). HTTP (`TriggerController`): `POST /trigger` → **202 Accepted** with `Location
/trigger/{id}`; `GET /trigger/{id}` → status in the current tenant. The controller sets neither the code nor
the Location by hand: it carries `@ChenileResponseCodes(success = 202, warning = 202)` and returns the
`TriggerResult` through the normal `process(...)` path.

### Header-aware responses (`ResponseHeadersAware`)

`TriggerResult` (a record holding `triggerId`) supplies its HTTP `Location` header by implementing
`org.chenile.base.response.ResponseHeadersAware` from **chenile-base** — the "header aware interface". A
response DTO opts into setting response headers by overriding `Map<String, List<String>> getResponseHeaders()`
(here `{"Location": ["/trigger/" + triggerId]}`), annotated `@JsonIgnore` so the headers never leak into the
JSON body. Chenile's HTTP layer reads the interface and applies the headers **uniformly**, so the business
object owns its headers with no servlet dependency and the same contract works for HTTP and in-JVM entry
points. Reach for it (instead of hand-building a `ResponseEntity`) whenever a Chenile response needs to carry
HTTP headers such as `Location`, `ETag`, or `Content-Disposition`.

`crontab-service` ships durable Quartz crontabs (`chenile_crontab`). `CrontabScheduler.fire` builds a
`TriggerInput` with `idempotencyKey = "crontab:<id>:<fireInstanceId>"`, `eventId = crontab.eventName`,
headers including `x-chenile-trigger-source=CRON`, `x-chenile-crontab-id`, Quartz fire details, and
`payload = crontab.eventPayloadJson`. Schedules from DB or classpath JSON (`JsonCrontabRepository`), validated
by `CrontabValidator`; Quartz syntax with seconds; single scheduler owner.

## Management API and admin console

Optional admin API at `/process-management/api` (`ProcessManagementController`, gated by
`chenile.process.management.enabled=true`), plain JSON DTOs. Endpoints: `GET /info`; paginated
`GET /processes` + `GET /processes/{id}` (returns `{ "process": ... }`); `GET /executions` — **trigger history
as a filtered view of `DISPATCH_TRIGGER` outbox rows** (via `ProcessOutboxRepository.findCommands/findByIds`),
filters `triggerId`, `crontabId` (from the command's context JSON), `status`, `page`, `size`, returns
`TriggerStatus`; `GET`/`POST`/`PUT` `/crontabs`; `POST /triggers`; `GET`/`POST`/`PUT` `/definitions` +
`POST /definitions/refresh`; `GET /trace?processId=…|triggerId=…` (tenant-scoped causal graph,
`PROCESS_CREATE`/`SUBPROCESS`/`SUCCESSOR` edges, refuses >1000 nodes with 413). Auth (`ManagementApiFilter`):
`X-Process-Management-Key` (constant-time compare, ≥32 chars) + `x-chenile-tenant-id`; key administers ALL
tenants; with `protect-all-http-routes=true` guards `/*`. `process-admin-server` packages this as a runnable
host (fails fast without key/protection/PG outside `dev`; `ddl-auto=validate`, `sql.init.mode=never`; defaults
DB configurator + in-VM worker delivery, ships no business workers; binds `127.0.0.1`). `process-ui` keeps the key in memory,
behind a same-origin HTTPS proxy, and offers a Quartz cron builder on the crontab form. See `docs/process-management-ui.md`.

## Multi-tenancy, completion, chaining

Tenant from `x-chenile-tenant-id`, persisted as `BaseJpaEntity.tenant`, propagated to sub-processes, worker
context (the q-based starter sets it on every work message from `process.tenant`; listeners reject work with no
tenant), trigger commands and completion events. A terminal process emits a transport-neutral
`ProcessCompletedEvent` (`generatedAt` from terminal `stateEntryTime`). No completion snapshot table:
`EMIT_COMPLETED` publishes `ProcessCompleted` (the framework-chaining subscriber creates successors) without
persisting a history row. Completion is read from the process's terminal status + state-entry time; cycles
rejected.

## Data model (tables)

Infrastructure tables ship as explicit SQL (and optional Liquibase); entity tables are Hibernate-mapped.
Entity tables carry Chenile base-class columns (`id` PK, `tenant`, created/modified timestamps, `version`,
and — for `AbstractJpaStateEntity` — current STM state + `stateEntryTime`), snake_case physical naming.
Reference DB: PostgreSQL.

- `process_table` (entity `Process`): `leaf`, `process_type`, `trigger_id`, `split_completed`,
  `completed_percent`, `parent_id`, `predecessor_id`, `description`, `num_sub_processes`,
  `num_completed_sub_processes`, `input` TEXT, `output` TEXT (+ base). `parent_id`/`predecessor_id` are
  self-references to `process_table.id`. Management indexes on `(tenant, created_time, id)`,
  `(tenant, trigger_id)`, `(tenant, parent_id)`, `(tenant, predecessor_id)`.
- `subprocess_error` (entity `SubProcessError`): `process_id`, `time_of_completion`, `exception_message`,
  `stack_trace` (+ base). Validation strings in `subprocess_error_validation_errors`; linked from
  `process_table` by a Hibernate join table (default `process_table_errors`).
- `process_definition` (entity `ProcessDefinition`): `process_type` (PK), `definition` TEXT (ProcessDef JSON).
  No tenant and no version column.
- `chenile_process_work_item` (SQL): JDBC worker queue — `id` PK, `process_id`, `process_type`, `worker_type`,
  `idempotency_key` UNIQUE, `payload`, `status`, `attempt`, `locked_by`, `locked_until`, `created_at`,
  `updated_at`, `finished_at`, `error_message`. Indexes `(status, locked_until)`,
  `(process_id, worker_type, status)`. (Provisioned only by JDBC-starter hosts; the admin host is in-VM.)
- `chenile_process_outbox` (SQL): the one durable command table — holds BOTH process-consequence commands AND
  trigger commands. `id` PK, `process_id` (NULL for `DISPATCH_TRIGGER`), `command_type` (registry discriminator:
  CREATE_SUBPROCESS/SIGNAL_PARENT/EMIT_COMPLETED/START_WORKER/DISPATCH_TRIGGER), `payload` (command-owned JSON;
  for triggers, the event envelope), `idempotency_key` UNIQUE (enqueue de-dup / trigger dedup), `status`,
  `attempt`, `visible_after`, `locked_by`, `claim_token` (fencing), `tenant_id`, `locked_until`, `created_at`,
  `updated_at`, `finished_at`, `error_message`. Indexes `(status, visible_after, locked_until)`, `(process_id)`.
- `chenile_process_receipt` (SQL): effect-level idempotency ledger behind `checkIdempotency(consumer, key)`;
  PK `(consumer, receipt_key)`, `received_at`. Append-only; prune on a retention horizon.
- `chenile_crontab` (entity `Crontab`): `name` UNIQUE, `enabled` (indexed), `cron_expression`, `timezone`,
  `event_name`, `headers_json`, `event_payload_json` (+ base).

**Removed tables**: `trigger_log` (triggers now live in `chenile_process_outbox` as `DISPATCH_TRIGGER`),
`chenile_trigger_execution` (older), `chenile_process_completion_event` (completion derived from terminal
status/state-entry time). There is NO dedicated trigger table.

### Schema management (explicit SQL or opt-in Liquibase)

Raw SQL per owning module: `chenile-process-outbox-schema.sql` + `chenile-process-outbox-json-migration.sql`
(chenile-outbox), `chenile-process-work-schema.sql` (jdbc-process-starter),
`chenile-process-management-history-schema.sql` + `chenile-process-completion-event-removal.sql`
(process-service). **No trigger schema SQL** (the trigger table is gone). Opt-in Liquibase changelogs under
each module's `src/main/resources/db/changelog/`, aggregated by
`process-admin-server/.../db/changelog/db.changelog-master.xml`, which aggregates **three** files: outbox,
history, reference (the admin host is in-VM, so the JDBC `work` changelog is NOT aggregated — a JDBC-starter
host includes `jdbc-process-starter`'s own `chenile-process-work.changelog.xml`). Liquibase does not run
unless a host adds the dependency and sets `spring.liquibase.change-log` (+ contexts): `chenile-process-jdbc`
(work, only for JDBC hosts), `chenile-process-outbox` (outbox + receipt), `chenile-process-history`
(process_table indexes + drop retired completion table), `chenile-process-reference` (process_definition). Guarded preconditions (`onFail=MARK_RAN`). STM/base-entity
tables (`process_table`, `subprocess_error`, `chenile_crontab`) are left to Hibernate or `liquibase diff`.
(There is no longer a trigger_log changeset.)

## Deployment topology (server + worker mini monoliths)

Production runs as ≥2 Chenile mini monoliths, scalable to more (`docs/deployment.md`):

- **Process Manager Server** (the brain): packages `process-service`, the always-on `chenile-outbox`, one
  `WorkerStarter` (preferably the **q-based** one), `trigger-service` + `crontab-service`, the management API /
  UI. Owns the one PostgreSQL datasource and the outbox poller. Dispatches work; exposes `ProcessManager` over
  HTTP (Chenile service `processService`) for worker callbacks.
- **Process Manager Worker** (the muscle): packages `process-delegate` (the `ProcessManagerClient` proxy +
  the typed listener bases and selectors), one or more worker jars (beans named `<processType>Executor`,
  `<processType>Splitter`, `<processType>Aggregator`), a headless `ProcessWorkListener`
  (`@ChenileController(serviceName="_processWorkService_", serviceSelector="processWorkServiceSelector")`,
  `@EventsSubscribedTo`, `@BodyTypeSelector("processWorkBodyTypeSelector")`, `accept(String processType, String
  workerType, @ChenileBody WorkListenerInput<Object>)`), and Chenile Kafka's consumer on the topic. Holds no
  process state; needs no process DB. Started with `process.manager.base-url` (read by `DelegateConfiguration`
  to build the proxy).

Loop: cron/trigger → `DISPATCH_TRIGGER` → `ProcessCreate` → STM → `START_WORKER` → q-based starter publishes a
`WorkListenerInput` (+ `processType`/`workerType` headers) → the listener's service selector picks the worker bean,
the body selector types the payload → work runs → HTTP callback
(`splitDone`/`doneSuccessfully`/`aggregationDone`) → STM advances → repeats to terminal → `EMIT_COMPLETED`
chains successors. Scale by adding worker monoliths/instances (per-process-type topics, KEDA on queue depth);
the one server is replicated for availability, not throughput. This whole deployment is scaffolded by the
**`chenile-process-management`** jgen blueprint (2.1.35) — which composes `minimonolith` +
**`chenile-process-worker-set`** to emit `<app>Server`, `<app>Worker` (headless Kafka `worker-listener`),
per-definition worker JARs, and an optional registry — over Kafka transport. The stock `process-admin-server`
uses the in-VM starter and ships no workers; use the blueprint for a real deployment. See the `chenile-jgen`
skill and `docs/blueprints/process-deployment-blueprint.md`.

### 2.1.35: typed process work listeners (supersedes the 2.1.34 shared BatchServiceBase)

- **Routing by `serviceSelector`.** `_processWorkService_` is now `ProcessWorkServiceFallback`, which *throws*
  `NO_PROCESS_WORKER_SELECTED` — it only runs if selection failed. Real dispatch is chenile-core's
  `serviceSelector`: `processWorkServiceSelector` returns `<processType>` + `Executor|Splitter|Aggregator`
  (e.g. `item` + EXECUTOR → bean **`itemExecutor`**) from the `processType`/`workerType` message headers. Worker
  beans **must** follow this naming. `DelegateConfiguration` imports both selectors.
- **Typed payloads by body selector.** `processWorkBodyTypeSelector` resolves the selected bean's
  `WorkListenerService<T>` type argument (Spring `ResolvableType`) and sets the exchange body type to
  `WorkListenerInput<T>`, so `input.payload` arrives as the worker's own class.
- **Worker signatures.** Executor: `Out doStart(WorkListenerInput<In>)` → `doneSuccessfully`. Splitter:
  `List<SubProcessPayload> doStart(WorkListenerInput<In>)` → `splitDone` (plus `splitPartiallyDone(...)`,
  `makeSubProcessPayload(child, childType)`). Aggregator: a **fold**, `Out doStart(Out soFar, WorkListenerInput<In>,
  ChildOut childOutput, Process child)` called once per immediate child (first call gets `null`), then
  `aggregationDone`. `progressUpdate(input, percent)` is available to all.
- **Failure semantics (changed).** `AbstractWorkListener.accept` restores the Chenile context afterwards and:
  - a worker's **own exception** is caught and reported as `doneWithErrors` / `splitDoneWithErrors` /
    `aggregationDoneWithErrors` (with stack trace and any `ErrorNumException` errors) — a business failure the
    process records (→ `PROCESSED_WITH_ERRORS`); the message is acknowledged, **not** retried;
  - if **reporting** that failure fails, it throws `WORKER_CALLBACK_FAILED` → Kafka retry → `.DLT`;
  - **malformed deliveries** (no `processId`, no `processType`, a `workerType` mismatch, no tenant in context)
    throw → Kafka retry → `.DLT`.
- **Generated code / sample.** The jgen process blueprints generate the listener and workers in this shape; the
  generated `doStart` hooks now return defaults (they no longer throw). `chenile-samples/p1` is migrated
  (package `org.chenile.samples.p1`).

### 2.1.34 deployment refinements (historical — the listener part is superseded above)

- **One shared, concrete worker service.** `BatchServiceBase` (in `process-delegate`) was made **concrete**
  and wired as the shared bean **`_processWorkService_`** in `DelegateConfiguration`. (2.1.35 replaced this with
  the selector-routed typed listeners.)
- **Worker/callback failures -> Kafka retry -> dead-letter.** In 2.1.34 a failing worker let the exception
  propagate to Kafka retry/DLT. (2.1.35 narrows this: only callback and delivery failures do.) There is **no
  server-side Kafka publisher** — the server publishes only through the durable outbox; the worker side owns
  delivery, retry and dead-lettering.
- **Header-scoped publication.** `QueueBasedProcessStarter` forwards only `x-`-prefixed headers to Kafka
  (so `x-chenile-tenant-id` et al. ride along; internal transport props are dropped).
- **Worker modules via `chenile-process-worker-set`.** The process-management aggregate composes `minimonolith`
  with the **`chenile-process-worker-set`** blueprint, which expands one worker module per process definition
  (owning the per-definition iteration and validation).

## Testing conventions

Integration tests (`TestFeeds`, `TestFile`, `TestChunks`) drive the recursive feed→file→chunk cascade with
fake workers resolved by naming convention. `chenile-outbox` tests: registry, rollback-together, idempotent
enqueue, SKIP LOCKED, backoff, retry-then-DEAD, dead-letter compensation, replay-safe parent counting, plus an
opt-in real-PostgreSQL suite. `trigger-service` tests: durable acknowledgement, unchanged-payload dispatch,
tenant isolation, submission uniqueness (outbox idempotency), status. `process-admin-server` integration test
drives create→chain over real HTTP (in-VM delivery; it PATCHes completion itself, no work-item assertion).
`ProcessWorkListenerTest` (process-delegate) covers typed dispatch, payload resolution, worker callbacks, tenant
context; `QueueBasedProcessStarterTest` covers the envelope, headers and legacy publishing.
Management API has HTTP integration contracts; `process-ui` has Vitest + Playwright. jgen-generated server/worker
projects test over Kafka via `KafkaBaseTest` (Testcontainers; Docker required).

## Comparison with Temporal (summary)

Chenile = orchestration **as data** (STM + process rows in your DB, outbox making transition consequences
durable); Temporal = orchestration **as code** (replayed deterministically on a cluster). For the cascade
Chenile models they are in the same class on durability and exactly-once; non-transactional/non-idempotent
effects are at-least-once in both. Temporal is broader; Chenile is simpler to operate and ships an admin
console + management API (dashboard, execution history as a filtered view of `DISPATCH_TRIGGER` rows, causal
trace graph). Anchor: Chenile ≈ Step Functions / transactional-outbox saga; Temporal ≈ durable-code.

## Gotchas / review checklist

- The outbox module is **`chenile-outbox`** (was `process-outbox`); the Java package is unchanged
  (`org.chenile.orchestrator.process.outbox`). It is a general-purpose durable outbox — processes AND triggers
  use it.
- Two producers (`OutboxCommandProducer<ProcessTransition>` and `OutboxCommandProducer<OutboxCommand>` for
  triggers), one registry, one dispatcher, one `chenile_process_outbox` table, **five** command types incl
  `DISPATCH_TRIGGER`. Eligibility is `shouldEnqueue` (no writes); the write is `enqueue`. There is no
  `Submission` wrapper — `DispatchTriggerCommand` is an `OutboxCommandLifecycle<OutboxCommand>`.
- Context install is centralized in the repository boundary (`handleAndComplete` installs `executionHeaders` +
  tenant and retains through commit). `AbstractProcessOutboxCommand.dispatch`/`onDead` still install tenant for
  the direct-call path (`ProcessCommandTenantTest`); don't strip that without rewriting the test.
- HTTP responses carry headers via the **header-aware interface** `ResponseHeadersAware` (chenile-base): a
  response DTO overrides `getResponseHeaders()` (`@JsonIgnore`) and Chenile applies them uniformly (e.g.
  `TriggerResult` → `Location`), so controllers don't hand-build `ResponseEntity` headers.
- **No `trigger_log`, no `TriggerObserver`, no separate trigger table.** A trigger is a `DISPATCH_TRIGGER`
  outbox command (`process_id` null). Trigger idempotency IS the outbox `idempotency_key` guard
  (`trigger:…` / `crontab:<id>:<fireInstanceId>`). `status`/`/executions` read `DISPATCH_TRIGGER` rows.
- `TriggerService.trigger` commits durable acceptance in a REQUIRES_NEW tx and returns the outbox row id;
  execution is the dispatcher's job. `POST /trigger` → 202 + `Location /trigger/{id}`.
- The three idempotency guards are distinct: outbox `idempotency_key` (enqueue de-dup, incl triggers),
  `claim_token` fencing (one winner per attempt), `checkIdempotency()`/`chenile_process_receipt` (effect-level
  exactly-once, keyed by business identity). Keep the receipt table (prune on a retention horizon).
- One DataSource + transaction manager for state, outbox, receipts; enqueue must join the producing
  transaction (process side) or the acceptance tx (trigger side), not an unrelated one.
- `SIGNAL_PARENT` counts each child once via the `PARENT` receipt; `CHAIN` prevents duplicate successors on
  replay.
- Worker bases live in **process-delegate**: use the typed `ExecutorWorkListener`/`SplitterWorkListener`/
  `AggregatorWorkListener` (2.1.35); `SplitterBase`/`ExecutorBase`/`AggregatorBase`/`BatchServiceBase` are legacy.
  Workers call back via `ProcessManagerClient` → proxy at `process.manager.base-url`.
- Worker **bean names are routing keys**: `<processType>Executor|Splitter|Aggregator`. A misnamed bean surfaces
  per message (the selected bean is resolved at request time), never at startup — and a message reaching
  `_processWorkService_` means selection failed (`NO_PROCESS_WORKER_SELECTED`).
- A worker exception is a *business* failure (reported as `...WithErrors`, no retry); only callback/delivery
  failures go to Kafka retry and the DLT. Provision the `.DLT` topics.
- Keep `docs/puml/process-states.mermaid` in sync with `process-states.xml`.
- Add new outbox commands by registering an `OutboxCommandLifecycle` bean with a stable `type()`,
  business-identity idempotency keys for non-idempotent effects, and an `onDead` if it needs compensation.
- `ProcessOutboxRepository` is **intentionally hand-written JDBC / native SQL, not JPA** — don't suggest
  porting it. It's a concurrent work queue whose correctness depends on Postgres primitives JPA can't express
  safely/portably: `FOR UPDATE SKIP LOCKED`, `ON CONFLICT DO NOTHING` (required so an enqueue/`checkIdempotency`
  conflict can't abort the shared `Process` business transaction — a JPA persist-and-catch would poison it),
  and single-statement rowcount-fenced compare-and-set (`status='RUNNING' and claim_token=?`). Rows map to a
  detached `OutboxCommand` DTO, never a managed entity. If more ORM is ever wanted, keep the hot path native
  and model only the cold read/admin finders as a read-only `@Entity` — hybrid, not conversion. Rationale in
  `docs/process-outbox.md` ("Why the repository is JDBC, not JPA") and ADR 0001.
- The management key administers all tenants; never ship it in a browser bundle/URL/log; serve over HTTPS.
- Liquibase changelogs are opt-in and context-gated. Four module changelogs exist
  (work/outbox/history/reference; no trigger changeset), but the admin master aggregates only three —
  `work` is JDBC-host-only since the admin host is in-VM. Don't hand-author DDL for base-entity/STM tables.
- `process-admin-server` uses the **in-VM** starter (depends on `invm-process-starter`, not
  `jdbc-process-starter`) and ships no business workers by design — a `START_WORKER` no-ops and a leaf sits in
  EXECUTING. It's for running the engine/API/scheduler; generate real deployments with the
  `chenile-process-management` jgen blueprint (2.1.35) — server + Kafka worker-listener + per-definition worker
  JARs (via `chenile-process-worker-set` → `chenile-process-workers`) + optional registry. The generated server uses the
  **q-based (Kafka)** starter; `jdbc-process-starter` is retained for hosts that want a DB work queue instead.
